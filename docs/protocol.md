# Wire protocol

Version **1**. Pinned **2026-10-03** (S1). This document and `packages/protocol` change together, in
one commit, always (CLAUDE.md § Other rules); `tests/protocol-doc.test.ts` holds the message, event,
error and rules tables below to the code.

One WebSocket per player, at `/play`. Every frame is a **binary** message; a text frame is a
protocol error. A frame is one message: a type byte, then its fields in the order given here,
**little-endian**, with no padding and no length prefix — the frame is the length.

The *why* lives in the ADRs: [ADR-0001](adr/ADR-0001-server-authority-and-prediction.md) (who
decides, who predicts), [ADR-0002](adr/ADR-0002-shells-fast-forwarded.md) (where a shell starts)
and [ADR-0003](adr/ADR-0003-websocket.md) (why a WebSocket).

## 1. Invariants

1. **The server is the only authority.** A client sends inputs — a direction to drive, a direction
   to aim, a trigger. Never a position, a hit, a score or a time it wants believed.
2. **A client is sent only what lies within its view**, plus the room's roster and kill feed. Not in
   a snapshot, an event, an error or a debug surface. A wallhack is a leak with no recovery.
3. **Every inbound frame is decoded before it is believed, on both sides**, and a malformed frame is
   refused as a value — never a throw, never a guess. The server closes the socket after three; the
   client treats one as deploy skew (§ 7).
4. **The world is integers.** Lengths in eighths of a unit, directions in 1,024ths of a turn, time in
   ticks. What the wire carries is the world at its own resolution, not a rounding of it — so a
   client that steps the same inputs from a snapshot computes the server's own next state (§ 2).
5. **A snapshot is a delta against the previous snapshot on the same socket.** The first one on a
   socket is a delta against nothing. A client that cannot apply one does not guess: it reconnects
   (§ 5).
6. **A shell on the wire is a starting condition, not a position.** It is sent once, as it enters a
   view; the client flies it on with `sim`'s own step and is told only when it is gone (§ 5.3).

## 2. Units

| Quantity | Unit | On the wire |
| --- | --- | --- |
| Length | **eighth** of a unit; a tank is 24 units (192 eighths) in radius | coordinates `u16`, `0 … 16383` (the arena is 2,048 units) |
| Direction | **1/1,024 of a turn**; 0 along +x, 256 along +y (the screen's down) — clockwise on screen | 10 bits |
| Time | **tick**, 1/30 s; the server's tick counter starts at 0 when the room opens | `u32` |
| Speed | eighths per tick | — (a rule, § 8) |

A direction's vector is a lookup in `geom`'s table — `COS[d]`, `SIN[d]`, both scaled by 2^14 —
generated by [`packages/geom/golden/directions.py`](../packages/geom/golden/directions.py) and
built exactly symmetric from its first octant. A step of `s` eighths in direction `d` is
`(round(COS[d]·s / 2^14), round(SIN[d]·s / 2^14))`, rounding half away from zero. Everything in this
paragraph is an IEEE 754 operation on integers and so the same in every engine; nothing in `sim` or
`geom` may call `Math.sin` (CLAUDE.md § Purity and exactness).

Reflection off an axis-aligned face is an operation on the index: off an `x` face (a wall's left or
right side) `d → 512 − d`; off a `y` face `d → −d`; off a corner `d → d + 512` (all mod 1,024).

## 3. Connection

```
client                                   server
  │ ── hello {version, token?, name} ──▶ │   the first frame, within 5 s of opening
  │ ◀── welcome {you, token, tick, …} ── │   or error {VERSION | NAME | FULL}, then close
  │ ◀── roster ───────────────────────── │   and again whenever names or scores change
  │ ◀── snapshot (against nothing) ───── │   then one per tick
  │ ── input {seq, aim, move, fire} ───▶ │   one per client tick
  │ ── ping {id} ──────────────────────▶ │   every 2 s, more often while syncing
  │ ◀── pong {id, tick, offsetUs} ────── │
```

- **The first two bytes of `hello` never change** — type `0x01`, then the version — so a server can
  always answer an old or new client with `VERSION` rather than `MALFORMED`.
- **Resume.** `welcome` carries a 16-byte token. A socket that drops keeps its tank in the room for
  `resumeGrace` ticks (§ 8); a `hello` carrying the token within it gets the same tank back,
  `resumed` set, and a fresh snapshot against nothing. After it, the token is forgotten and the
  same `hello` joins as a new player, `resumed` clear.
- **The clock.** A `pong` says which tick the server was in when it answered and how far into it,
  in microseconds. The client keeps the samples with the smallest round trips and runs its own tick
  aligned to the server's (C0).

## 4. Messages

| Message | Type | Direction | Bytes |
| --- | --- | --- | --- |
| `hello` | `0x01` | client → server | 4 + name, 20 + name with a token |
| `input` | `0x02` | client → server | 9 |
| `ping` | `0x03` | client → server | 3 |
| `welcome` | `0x81` | server → client | 26 |
| `snapshot` | `0x82` | server → client | 19 at least: a 14-byte head, five counts, their entries (§ 5) |
| `roster` | `0x83` | server → client | 2 + 6 and a name per entry |
| `pong` | `0x84` | server → client | 9 |
| `error` | `0x85` | server → client | 2 |

A type byte the receiver does not know is `MALFORMED`. So is a frame that ends early ("truncated"),
one with bytes left over ("trailing bytes"), a reserved bit set, or a value outside its field's
range below.

### 4.1 `hello` — `0x01`

| Field | Type | |
| --- | --- | --- |
| type | `u8` | `0x01` |
| version | `u8` | `PROTOCOL_VERSION`, 1 |
| flags | `u8` | bit 0: a token follows; the rest 0 |
| token | 16 bytes | only with flag bit 0 |
| name | `u8` length + UTF-8 | see below |

**A name** is 1–16 code points and at most 48 bytes of strict UTF-8 (no overlong forms, no
surrogates), with no leading or trailing whitespace and none of: C0 and C1 controls, DEL, U+2028,
U+2029, the bidi embeddings and overrides U+202A–U+202E, the isolates U+2066–U+2069. A name that
flips the scoreboard's text is a name that lies about who killed whom. The decoder refuses an
invalid name as `MALFORMED`; the server answers it with `NAME`.

### 4.2 `input` — `0x02`

| Field | Type | |
| --- | --- | --- |
| type | `u8` | `0x02` |
| seq | `u32` | 1, 2, 3 … per socket; never 0 |
| bits | `u32` | aim bits 0–9 · move bits 10–19 · moving bit 20 · fire bit 21 · bits 22–31 zero |

`move` is meaningful only with `moving` set; without it, its bits must be 0. One input per client
tick. The server applies a socket's inputs one per tick in `seq` order (S3) and reports the last it
applied as every snapshot's `ack`.

### 4.3 `ping` — `0x03`

| Field | Type | |
| --- | --- | --- |
| type | `u8` | `0x03` |
| id | `u16` | the client's own counter; it remembers when it sent each |

### 4.4 `welcome` — `0x81`

| Field | Type | |
| --- | --- | --- |
| type | `u8` | `0x81` |
| version | `u8` | the server's `PROTOCOL_VERSION` |
| you | `u16` | your tank's entity id |
| token | 16 bytes | from a CSPRNG; keep it to resume |
| tick | `u32` | the room's tick now |
| flags | `u8` | bit 0: resumed; the rest 0 |
| arena | `u8` | which arena the room plays (S2 pins arena 0) |

### 4.5 `roster` — `0x83`

| Field | Type | |
| --- | --- | --- |
| type | `u8` | `0x83` |
| count | `u8` | at most `roomSize` |
| per entry: id | `u16` | the tank's entity id |
| flags | `u8` | bit 0: a bot; the rest 0 |
| score | `u16` | kills since joining |
| name | `u8` length + UTF-8 | § 4.1's rules |

Sent whole, whenever a player joins or leaves or a score changes.

### 4.6 `pong` — `0x84`

| Field | Type | |
| --- | --- | --- |
| type | `u8` | `0x84` |
| id | `u16` | the ping's |
| tick | `u32` | the tick the server was in when it answered |
| offsetUs | `u16` | how far into that tick, in µs; less than 33,334 |

### 4.7 `error` — `0x85`

| Field | Type | |
| --- | --- | --- |
| type | `u8` | `0x85` |
| code | `u8` | § 7 |

The server sends it and closes the socket.

## 5. Snapshots — `0x82`

### 5.1 Layout

| Field | Type | |
| --- | --- | --- |
| type | `u8` | `0x82` |
| tick | `u32` | the tick this view is of |
| ack | `u32` | the last input `seq` applied for you; 0 before any |
| self.reload | `u8` | ticks until you may fire, `≤ reload` |
| self.shells | `u8` | your shells in the air, `≤ maxShells` |
| self.respawn | `u8` | ticks until you respawn; 0 while alive; `≤ respawn` |
| self.shield | `u8` | ticks of spawn shield left, `≤ shield` |
| crates | `u8` | a bit per crate spot holding a crate; bits past `crateSpots` zero |
| tanks.removed | `u8` count + `u16` ids | tanks that left your view (or the room) |
| tanks.updated | `u8` count + entries | below |
| shells.removed | `u8` count + `u16` ids | shells that left your view or died |
| shells.added | `u8` count + entries | below |
| events | `u8` count + entries | § 6 |

**A tank entry:** `id u16`, `mask u8`, then the fields the mask names, in this order:

| Mask bit | Field | |
| --- | --- | --- |
| `0x01` absolute position | `x u16`, `y u16` | |
| `0x02` relative position | `dx i8`, `dy i8` | added to the baseline's position |
| `0x04` state | 24 bits as `u16` + `u8` | hull bits 0–9 · turret 10–19 · hp 20–21 · shield 22 · alive 23 |

A mask of 0, both position bits, or a reserved bit is `MALFORMED`.

**A shell entry** (11 bytes): `id u16`, `owner u16`, `x u16`, `y u16`, `bits u16` (dir bits 0–9 ·
bounced bit 10 · the rest zero), `age u8` (ticks flown, `≤ shellLife`).

### 5.2 Deltas

A server keeps, per socket, the last **view** it sent — the whole of what that client could see at
that tick — and sends the next as a delta against it. The rules, as `protocol.diff` implements and
`protocol.apply` checks them:

- A tank in the new view and not the old is sent whole: absolute position and state.
- A tank in both is sent only for what changed: its position as a relative step when each axis moved
  at most 127 eighths (a tank drives 59 a tick, so always, short of a respawn), else absolute; its
  state only if any of it changed. A tank that changed nothing is not sent.
- A tank in the old view and not the new is in `removed`.
- A client applying a delta refuses one that removes or steps a tank it does not hold, updates one
  twice, gives a new one less than whole, or moves one off the arena — and reconnects.

**Why no acknowledgements.** A delta protocol over UDP needs the client to acknowledge snapshots,
because a datagram may never arrive and the server must diff against one that did. Over a WebSocket
(TCP, [ADR-0003](adr/ADR-0003-websocket.md)) every frame sent on a socket either arrives, in order,
or the socket dies with it — so the last frame *sent* is the baseline, and a new socket starts
against nothing. The `ack` a snapshot carries acknowledges the client's *inputs*, which prediction
replays from (ADR-0001); it is not a snapshot acknowledgement.

### 5.3 Shells are starting conditions

A shell flies straight at `shellSpeed`, bounces off a wall once by § 2's reflection, and dies on its
second wall, on any tank, or at `shellLife`. Every step of that is integer `geom` and the same in
every engine, so the wire does not carry a shell's position every tick. A shell is in `added` once —
on the tick it enters a client's view, with its state *at that tick* — and the client steps it
forward with the same function the server uses. It is in `removed` once, when it dies or leaves the
view; how it died is an event (§ 6). A shell already held is never re-sent; `apply` refuses one
added twice.

### 5.4 The budget

At 12 tanks driving, each a 5-byte relative update, plus the 14-byte head and the five counts:
about 80 bytes a tick, 2.4 KB/s, before shells and events — which are sent once each, not per
tick. The budget is **6 KB/s down per client** (ROADMAP S4); `tools/bench` measures it.
`roundtrip.test.ts` holds a randomly moving world of ~12 tanks and ~10 shells under 200 bytes a tick
on average.

## 6. Events

Events ride in the snapshot of the tick they happened in. Each is a type byte and its fields.

| Event | Type | Fields | Sent to |
| --- | --- | --- | --- |
| `shot` | `1` | `shell u16`, `seq u32` — your input that fired it | the shooter only — how a predicted shell finds its real one (C2) |
| `hit` | `2` | `shell u16`, `victim u16`, `hp u8` — after the hit | clients that see the victim |
| `kill` | `3` | `killer u16`, `victim u16`; the same id twice for a tank that shot itself | everyone in the room — the kill feed |
| `crate` | `4` | `spot u8`, `tank u16` — who picked it up | clients that see the spot |
| `spawn` | `5` | `tank u16` | clients that see where it spawned |

## 7. Errors

| Code | Byte | When | The client |
| --- | --- | --- | --- |
| `VERSION` | `1` | `hello`'s version is not the server's | says a newer version is out and reloads |
| `MALFORMED` | `2` | a frame failed to decode, three times on one socket | reports deploy skew; does not retry blindly |
| `NAME` | `3` | `hello`'s name breaks § 4.1 | asks for another name |
| `RATE` | `4` | more than twice the tick rate of inputs, for a second | reconnects after a pause |
| `FULL` | `5` | the server will not open another room | says so, retries later |

A client that receives a frame it cannot decode treats it as deploy skew: it says the page is out
of date and offers a reload.

## 8. Rules

The game's numbers, as `RULES` in `packages/protocol` — here, and in code, nowhere else. They are
part of the contract, not of `sim`, because the bots play by them and may not import `sim`.

| Rule | Value | Meaning |
| --- | --- | --- |
| `tickHz` | `30` | ticks a second; one snapshot to every client per tick |
| `arena` | `16384` | the arena's side in eighths — 2,048 units |
| `tankRadius` | `192` | 24 units |
| `tankSpeed` | `59` | eighths a tick along the hull — 221.25 units/s |
| `hullTurn` | `24` | directions a tick the hull may turn — ≈253°/s |
| `hitPoints` | `3` | |
| `shellRadius` | `48` | 6 units |
| `shellSpeed` | `160` | eighths a tick — 600 units/s |
| `shellLife` | `48` | ticks — 1.6 s |
| `shellBounces` | `1` | a shell dies on its second wall |
| `muzzle` | `256` | a shell is born this far from its tank's centre along the turret — 32 units |
| `reload` | `11` | ticks between shots — ≈367 ms |
| `maxShells` | `3` | a tank's shells in the air at once |
| `respawn` | `90` | ticks from death to respawn — 3 s |
| `shield` | `45` | ticks of spawn shield, in which the tank cannot fire — 1.5 s |
| `crateEvery` | `600` | ticks between crates — 20 s |
| `crateSpots` | `4` | |
| `crateRadius` | `128` | 16 units |
| `crateHeal` | `1` | hit points, up to `hitPoints` |
| `roomSize` | `12` | people and bots in a room |
| `botsFillTo` | `6` | bots fill a room to this many tanks and leave as people arrive |
| `resumeGrace` | `300` | ticks a dropped socket keeps its tank — 10 s |
| `fastForwardMax` | `3` | ticks a shell may be fast-forwarded by its shooter's half round trip — 100 ms (ADR-0002) |
| `inputQueueMax` | `4` | inputs a player may have queued; beyond it the oldest is dropped |

**Driving.** The stick names a direction. The hull turns toward it — or toward its opposite, when
that is nearer, and then the tank drives in reverse — by at most `hullTurn` a tick, and the tank
moves `tankSpeed` along the hull whenever the stick is held. The turret is the input's `aim`. A
tank that would overlap a wall or another tank is stopped against it (S2 pins how).

## 9. Deliberately not in v1

- **Snapshot acknowledgements** — TCP makes the last frame sent the baseline (§ 5.2).
- **Input redundancy** (each input repeated in the next few frames). It is how a UDP game survives
  a lost packet; a WebSocket loses no frame, it stalls them (ADR-0003).
- **Compression of frames** (`permessage-deflate`). Frames are small and already dense; the CPU
  and the latency are not worth the bytes. Measured, not argued, in S4.
- **Spectating, teams, chat.** Not this project's problem.
